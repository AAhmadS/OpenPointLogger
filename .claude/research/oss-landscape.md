# OSS landscape for Trailmark's export/citation/capture pipeline

Researched 2026-09-07 via live web search/fetch. Every project below was verified to exist
via a search result or fetched page at research time. Where a specific number (stars,
license, last-commit date) could not be pinned to a primary source, it is marked
**unverified** rather than guessed.

## 1. Immediately-usable open-source projects

### 1a. Markdown → HTML/DOCX/PDF conversion

| Project | URL | License | Stars (approx) | What it buys Trailmark | Integration cost/risk |
|---|---|---|---|---|---|
| **Pandoc** | https://github.com/jgm/pandoc | GPL-2.0 | large, long-established (exact current count unverified) | Universal converter: MD → DOCX, HTML, PDF (via LaTeX/Typst/WeasyPrint/wkhtmltopdf/pagedjs), EPUB, LaTeX. Handles footnotes, tables, citeproc citation processing natively (`--citeproc` + CSL). | **Best default for DOCX.** External binary (~40 MB Windows portable build, confirmed via Softpedia/pandoc.org), invoked via `subprocess` or `pypandoc`. Must be bundled alongside the PyInstaller onefile exe (extra data file), not compiled into Python. GPL-2 is a **license consideration**: Pandoc itself is a separate executable you shell out to, which is the standard way projects avoid GPL contamination of their own (differently-licensed) codebase — but confirm this stance if Trailmark ever moves to a non-GPL-compatible license story. |
| **markdown-it-py** | https://github.com/executablebooks/markdown-it-py | MIT | not confirmed numerically (unverified count) | Pure-Python, 100% CommonMark-compliant MD→HTML with a plugin system (footnotes, front-matter, definition lists). No external binary. | Low risk, pure Python, small footprint. Good for the **HTML** export path (no Pandoc needed) since Trailmark's HTML export is "self-contained" already. |
| **mistune** | https://github.com/lepture/mistune | BSD | not confirmed numerically (unverified count) | Fastest pure-Python MD parser, plugin renderers. | Alternative to markdown-it-py; pick one, not both. Mistune is faster; markdown-it-py has stronger CommonMark conformance and a bigger plugin ecosystem (used by Jupyter/MyST). For Trailmark's simple report structure either works — lean markdown-it-py for spec conformance. |
| **python-docx** | https://github.com/python-openxml/python-docx | MIT | ~4k (unverified exact) | Direct DOCX object model — headers, styles, tables, TOC — without shelling to Pandoc. | Good for **post-processing** a Pandoc-generated DOCX (fix styles, inject a real Word TOC field, set document properties) or for building DOCX from scratch if you want tighter control than Pandoc's default output. |
| **docxtpl** (python-docx-template) | https://github.com/elapouya/python-docx-template | LGPL-2.1 | ~2.7k (unverified exact, reported by search aggregator) | Jinja2-templated `.docx` — author a Word template with `{{ point.text }}` placeholders and loops, feed it structured data, get a filled DOCX. **This is the closest thing to "user-suppliable DOCX templates" that exists off the shelf.** | Directly matches the requirement "users must supply their own templates" for the DOCX target. LGPL is fine to depend on as a library (dynamic linking equivalent — Python import). Low integration cost. |
| **WeasyPrint** | https://github.com/Kozea/WeasyPrint | BSD | ~9.3k (confirmed via GitHub topic listing) | Pure-Python(ish; uses Pango/cairo native libs) HTML+CSS → PDF. Good CSS3 support (page breaks, `@page`, running headers/footers, `counter()` for numbered citations). No browser engine. | **Best fit for a template-driven, no-heavy-deps PDF pipeline** matching Trailmark's "fill an HTML template" plan. Ships native deps (Pango, cairo, GDK-pixbuf, fontconfig) — on Windows these must be vendored (GTK3 runtime or the `weasyprint` Windows wheels bundling libs); adds tens of MB to a PyInstaller build but nowhere near a browser engine's footprint. |
| **Typst** (+ Tectonic as LaTeX-alt) | https://github.com/typst/typst | Apache-2.0 | large and fast-growing (exact unverified) | Single self-contained **~15 MB** binary (confirmed via typst.app/open-source and release notes), 10x faster compiles than LaTeX, modern templating language with native JSON data ingestion — you can hand it a JSON dict and a `.typ` template and get camera-ready PDF with proper kerning/ligatures/math, without installing a TeX distribution. | **This is the highest-leverage pick for the "academic / LaTeX-grade typography" template purpose.** A LaTeX distribution (even Tectonic, a from-scratch Rust TeX engine) pulls in a package cache that can run to hundreds of MB on first compile; Typst is one ~15 MB binary, no runtime package fetching, and is explicitly designed to be embedded/scripted. Integration: shell out to `typst compile data.json template.typ out.pdf` or use the `typst` Python bindings. Learning curve for template authors is lower than LaTeX (real functions/variables, not TeX macros) which also matters if you want *users* to write templates. |
| **Playwright (Python) — Chromium PDF** | https://github.com/microsoft/playwright-python | Apache-2.0 | large (Microsoft-maintained; exact unverified) | `page.pdf()` via headless Chromium: pixel-perfect rendering of arbitrary HTML/CSS/JS (flexbox, grid, web fonts, canvas), matches exactly what a user previews in a browser. Benchmarks show warm Playwright PDF generation is dramatically faster than WeasyPrint per-page (single-digit ms once the browser is warm) though the browser itself is heavy to ship. | **Biggest downside: Chromium download is ~150–160 MB** (confirmed: Playwright docs / community reports put a single Chromium build at ~150-160 MiB, full three-engine install ~400 MB; a `--only-shell` trimmed install saves ~79%). For a "small no-heavy-deps desktop app" this is the worst-fit option size-wise, even though it gives the best CSS/JS-fidelity PDF. `pyppeteer` (the older pure-Python Puppeteer port) is **unmaintained** — do not adopt it new. |
| **wkhtmltopdf** | (legacy, WebKit-based) | LGPL/MIT dual | n/a | Historically the "cheap HTML→PDF" answer. | **Do not adopt.** It is widely reported as effectively unmaintained/deprecated across 2025-2026 sources found during this search (multiple "wkhtmltopdf alternatives in 2026" articles exist specifically because of this). WeasyPrint or Playwright supersede it. |

**Recommendation for the small, no-heavy-deps desktop build:**
Use a **two-tier PDF strategy** rather than one tool for everything:
- **Business-formal / personal / team / protocol templates** → **WeasyPrint** driven by an HTML+CSS template (fits the "fill an HTML template via tool calls" plan exactly, ~9-20 MB of extra native libs on Windows, no browser engine).
- **Academic / "research roam" LaTeX-grade typography** → **Typst** (one ~15 MB binary, best-in-class math/citation typesetting, far cheaper than a LaTeX distro or Tectonic's first-run package fetch).
- **DOCX** → **Pandoc** (shelled out, ~40 MB portable binary) as the default converter, with **docxtpl** as the answer to "user supplies their own DOCX template," and **python-docx** for any programmatic touch-ups Pandoc's output needs.
- Avoid Playwright/Chromium and wkhtmltopdf for the packaged desktop app; reserve headless-Chrome rendering (if ever needed for pixel-perfect HTML preview export) as an optional, separately-downloaded component rather than a bundled default, given the ~150 MB+ cost.
- Markdown parsing itself: **markdown-it-py** (MIT, pure Python, CommonMark-complete) as the single source-of-truth parser feeding both the HTML export and the Pandoc/WeasyPrint/Typst pipelines.

### 1b. Citation / reference management (real APA/IEEE/Chicago styles)

| Project | URL | License | Notes |
|---|---|---|---|
| **citeproc-py** | https://github.com/citeproc-py/citeproc-py (also actively maintained fork/org) | (BSD-family, confirmed on PyPI listing) | A Python **CSL 1.0.2 processor** — feed it CSL-JSON bibliography data + a `.csl` style file, get correctly formatted citations and bibliography in plain text/HTML/reStructuredText. This is precisely "cheap real citation styles" — CSL already defines APA, IEEE, Chicago, and ~2,000 other styles as data files, not code. |
| **citeproc-py-styles** | https://github.com/inveniosoftware/citeproc-py-styles | matches CSL styles' license (CC-BY-SA, per CSL project norms) | Ships the actual `.csl` style files (APA confirmed present) as an installable static-resource package, so you don't vendor the whole CSL styles repo by hand. |
| **CSL styles repository** | https://github.com/citation-style-language/styles | CC-BY-SA-3.0 | The canonical, community-maintained source of **every** citation style (APA, IEEE, Chicago author-date/notes, Vancouver, Harvard variants, thousands more) as CSL XML. This is the actual answer to "how do we support IEEE/Chicago cheaply": don't hand-code formatters, ship/fetch a `.csl` file and run it through citeproc-py. |
| **Pandoc's built-in `--citeproc`** | (part of Pandoc, above) | GPL-2.0 | If Pandoc is already in the pipeline for DOCX, its citeproc filter can format citations/bibliography from CSL-JSON + a `.csl` style directly during the MD→DOCX/PDF conversion — potentially **removing the need for a separate citeproc-py integration entirely** for the DOCX/PDF paths, while citeproc-py remains useful for in-app live preview of a formatted citation before export. |
| **Zotero `translation-server`** | https://github.com/zotero/translation-server | AGPL-3.0 (Zotero client itself is; verify translation-server's own license file before bundling) | Node.js server that runs the full library of Zotero's site-specific "translators" (hundreds of scrapers for journals, news sites, GitHub, etc.) and can also resolve **DOI/ISBN/PMID/arXiv** identifiers to full bibliographic metadata via a local HTTP API (port 1969 by default), self-hostable via Docker. | Turns "paste a link" into structured author/title/date/publisher/DOI metadata for a huge range of real-world sources — far broader coverage than generic readability heuristics for anything academic/news. **Cost:** requires bundling/spawning a Node.js service (heavier than a pure-Python dependency) and AGPL implications if it's linked into a distributed product rather than run as an arm's-length local service the app talks to over HTTP — treat it as an optional, separately-launched local service, not a compiled-in library, if AGPL is a concern. |
| **Citation.js** | https://github.com/citation-js (org; e.g. `citation-js/citation-js`) and its `plugin-zotero-translation-server` | MIT (Citation.js core) | JS citation formatting/parsing toolkit with a plugin that talks to a Zotero translation-server instance. Only relevant if any part of the pipeline moves to Node/Electron; for a Python app, citeproc-py + CSL styles is the direct equivalent. |

**Recommendation:** citeproc-py + citeproc-py-styles (or the raw CSL styles repo) gets Trailmark real APA/IEEE/Chicago output for the cost of one small pure-Python dependency plus a folder of `.csl` XML files — this is the single highest-leverage, lowest-risk pickup for the "just numbers sources [1][2] today" gap. Add Zotero `translation-server` **later**, as an optional local helper process, specifically to auto-populate structured citation metadata (author/year/publisher/DOI) for pasted URLs that trafilatura-style scraping can't resolve (paywalled journals, DOIs, ISBNs).

### 1c. URL → clean metadata / citation extraction

| Project | URL | License | Stars (confirmed) | Verdict |
|---|---|---|---|---|
| **Trafilatura** | https://github.com/adbar/trafilatura | Apache-2.0 | **~5,596** (confirmed via search result) | Best current all-rounder: actively maintained (2.0 shipped Dec 2024, regular 2024-2025 releases), extracts main text **and metadata** (author, title, date, sitename, categories), outputs to TXT/CSV/XML/TEI, and multiple independent benchmarks in the search results cite it as outperforming alternatives on extraction accuracy. **Recommended primary choice** for "pasted link auto-fills author/title/date/site." |
| **readability-lxml** | (readability fork ecosystem) | Apache-2.0 | **~2,895** (confirmed) | Good at stripping boilerplate to primary content (Readability.js-style), slower release cadence, weaker on structured metadata than Trafilatura — use as a fallback text-extraction pass, not primary. |
| **newspaper3k / newspaper4k** | https://github.com/codelucas/newspaper (3k, abandoned since Sept 2020 per search result) / community `newspaper4k` fork | MIT | newspaper4k **~1,062** (confirmed) | The original `newspaper3k` on PyPI is **abandoned — do not adopt new**; if this family is wanted at all, target `newspaper4k` specifically, which is API-compatible and still receives fixes. Trafilatura is the stronger default choice regardless. |
| **Zotero translators (via translation-server)** | see above | — | — | Broadest coverage for citation-shaped metadata (journals, DOIs) but heavier to run; complements Trafilatura rather than replacing it for general web pages. |

**Recommendation:** Trafilatura as the default "paste a link, get author/title/date/site" extractor (pure Python, no browser needed, actively maintained, best accuracy in the comparisons found). Consider a later optional Zotero translation-server hop specifically for DOI/ISBN/academic sources.

### 1d. Screenshot / OCR / clipboard on Windows

| Project | URL | License | Notes |
|---|---|---|---|
| **winocr** | https://pypi.org/project/winocr/ | (check package metadata; small utility, unverified license text) | Thin Python wrapper around the **built-in Windows.Media.Ocr** API — no external OCR engine to ship, uses the OCR language packs already on the user's Windows install. This is the natural fit for a Windows-only pywebview app: zero extra binary weight, decent accuracy, and it's literally "the OS's own OCR," which matches Trailmark's no-heavy-deps philosophy better than bundling Tesseract. |
| **pytesseract** + Tesseract OCR engine | https://github.com/tesseract-ocr/tesseract (Apache-2.0) / pytesseract wrapper | Apache-2.0 | Much more mature/tunable OCR, but requires bundling the Tesseract engine binary + trained-data language files (tens of MB), a real weight cost for a "lightweight" tray app already optimizing icon/window footprint (per recent commit history compressing icons and windows). Use only if winocr's accuracy proves insufficient for the target content (e.g., dense tables, code screenshots). |
| **NormCap** | https://github.com/dynobo/normcap (project referenced in search results) | (open-source, check its own license — GPL family typical for this class of tool; verify before reuse) | A full OCR-powered screen-capture *tool*, cross-platform (confirmed to target Windows too). Worth studying its Windows OCR + Tesseract dual-backend selection logic rather than shipping it wholesale — Trailmark already has its own capture flow (Ctrl+Alt+P panel), so this is a reference implementation, not a dependency. |
| **Clipboard capture** | `pywin32` (`win32clipboard`) or `pyperclip`/`Pillow.ImageGrab` | pywin32: PSF-style/BSD; pyperclip: BSD; Pillow: HPND-style | `PIL.ImageGrab.grabclipboard()` (Pillow — already a Trailmark dependency per the project brief) already reads an image off the Windows clipboard with zero new dependency. For text, `pyperclip` or the stdlib-adjacent `win32clipboard` both work; since Pillow is already in the stack, lean on `ImageGrab` first and only add `pywin32` if raw clipboard formats beyond image/text are needed. |

**Recommendation:** `winocr` (built-in Windows OCR, no bundling cost) for optional text-from-screenshot, and `Pillow.ImageGrab` (already a dependency) for clipboard screenshot capture — this whole capability can be added for near-zero binary-size cost, consistent with the project's recent "lightweight" push (icon compression, blur reduction, pagination commits visible in git log).

### 1e. Other high-leverage picks

- **Jinja2** (BSD, huge adoption) — if not already used, it's the natural templating engine to sit between "compose Markdown" and "fill an HTML/Typst/`.docx` template," and it's what docxtpl already builds on, keeping one templating mental model across all four export formats.
- **CSL-JSON** as the internal canonical citation data shape (rather than Trailmark inventing its own schema) — future-proofs interop with citeproc-py, Pandoc's citeproc, Zotero, and any future import/export of a user's existing Zotero/Mendeley library.

## 2. Is there a more complete OSS app to contribute to instead?

Searched specifically for the differentiator: **instant global-hotkey capture of a short point + attached source, grouped by topic, exported as a numbered cited report.**

| Project | What it does | Activity (as found) | License | Verdict on the gap |
|---|---|---|---|---|
| **Zotero** (+ **Zotero Better Notes** plugin, https://github.com/windingwind/zotero-better-notes) | Reference manager; Better Notes adds a connected note workspace where PDF/webpage annotations "flow" into structured notes, and can generate notes from multiple annotated items as a report-like output. Zotero's own `translation-server` already solves URL→citation metadata at high quality (see 1c). | Better Notes: active project with an ecosystem of sub-plugins (e.g. `zotero-af2n` for annotation flow) found in this search. | Zotero: AGPL-3.0-ish (verify per-repo); Better Notes: check its own LICENSE file (not confirmed here). | **Closest existing overlap for the citation/report half**, but Zotero's capture unit is a *document/reference*, not a **one-line typed point with instant global hotkey capture mid-workflow**. Zotero has no OS-wide hotkey for "jot a point right now" — its browser connector saves whole pages/items. Verdict: **genuine gap remains** for Trailmark's core interaction (frameless glass panel, Ctrl+Alt+P, typed point + inline source, grouped by topic) — but Trailmark's *report export* ambitions (numbered citations, styled report) could legitimately be built as **citeproc-py + CSL**, the same substrate Zotero itself uses, rather than reinvented. Not "build a plugin for Zotero instead" — the interaction model is too different — but reuse Zotero's citation substrate. |
| **Obsidian** + **Pandoc plugin** (https://github.com/OliverBalfour/obsidian-pandoc) + **obsidian-enhancing-export** (https://github.com/mokeyish/obsidian-enhancing-export) | Obsidian is proprietary core (plugins are open source) with a huge plugin ecosystem; the Pandoc plugin exports notes to DOCX/PDF/LaTeX/HTML with citation support via Pandoc's citeproc, matching almost exactly Trailmark's planned export pipeline. | Multiple maintained forks exist (`obsidian-community/obsidian-pandoc`, `RainCat1998` fork), suggesting the original may be low-activity and community-forked to keep alive — **treat original as possibly stalled; verify before depending on it**. | Obsidian app itself: **proprietary, not OSS** (free-to-use, not source-available) — disqualifies it as a "contribute instead" target for an MIT project wanting to stay fully open. Plugins are MIT-ish individually. | Obsidian is **not open source**, so "contribute to Obsidian instead" isn't available in the way the question frames it (no ability to add a native global-hotkey capture panel to closed-source core; only a plugin sandboxed inside Obsidian's UI, which cannot give the frameless always-on-top glass panel Trailmark has). Its Pandoc export plugin is, however, the **best available reference implementation to study/lift** for the templating subsystem (see section 3). |
| **SiYuan** (https://github.com/siyuan-note/siyuan) | Self-hosted, open-source ("privacy-first") knowledge workspace, block-based like Notion/Obsidian, with a browser web-clipper extension. | **~45.9k stars** (confirmed), described as very actively developed ("last commit 21 hours ago" reported in a search result at research time — treat as a snapshot, not a durable fact). | Open source (check exact license file; commonly AGPL-family for this class — not independently confirmed here). | Full-featured PKM competitor with web clipping, but same shape problem as Obsidian/Joplin: it's a **notebook**, not an **instant-capture-with-citation-report-export** tool. No evidence found of a global-hotkey "log one point with a source" workflow. A plugin could theoretically add one, but SiYuan's own block/notebook model is heavier than Trailmark's flat point-log; would fight the grain rather than extend it. |
| **Joplin** (https://github.com/laurent22/joplin) | Open-source, E2E-encryptable notes app with a web clipper. | **~56.3k stars** (confirmed), release v3.7.10 dated July 28 2026 in a search result (treat as a point-in-time snapshot). | MIT (widely known; not independently re-verified via LICENSE fetch in this pass — flag as **unverified in this session**). | Same verdict as SiYuan/Obsidian: mature note-taking app with clipping, no global-hotkey micro-capture-with-citation-report primitive. Its plugin API is genuinely extensible (it's fully OSS, unlike Obsidian) so "write a Joplin plugin" is at least *technically* available — but Joplin's data model (notebooks/notes) doesn't map cleanly onto "topic → sub-topic → numbered points → cited report," and a plugin can't easily deliver a frameless native always-on-top OS-level hotkey panel outside Joplin's own window chrome the way pywebview + a global hotkey library can standalone. |
| **Memos** (usememos, https://github.com/usememos/memos) | Self-hosted, markdown-native "quick capture" tool explicitly built for fast timeline-style notes, with an official **Web Clipper** (https://github.com/usememos/web-clipper) for saving pages/selections as Markdown. | Reported near **60,000 GitHub stars** at v0.28.0 (April 2026, per search result) and a web-clipper update as recent as Aug 27 2026 — **actively developed**. | Open source (Go backend; verify exact license before any contribution — not independently re-confirmed here). | **Closest philosophical cousin found**: quick-capture-first design, not notebook-first. But it is a **server/timeline app** (self-hosted service + web UI/clipper), not a native always-on-top global-hotkey desktop overlay, and it has no citation/report-export concept — it's closer to a self-hosted Twitter-for-yourself. A genuine gap remains for "grouped by topic → numbered cited report export," and bolting that onto Memos would mean rebuilding much of Trailmark's report-rendering logic against someone else's data model anyway. |
| **Karakeep** (formerly Hoarder) (https://github.com/karakeep-app/karakeep) | Self-hostable "bookmark everything" app: links/notes/images, AI auto-tagging, full-text/semantic search, browser extensions + mobile apps for quick bookmarking. | **28,000+ stars** (confirmed via search result). | Open source (verify exact license — not independently re-confirmed here). | Excellent at *capturing and organizing sources*, weak/absent on the "typed research point + citation + topic-grouped numbered report export" side — it's a bookmark/archive tool, not a writing/reporting tool. Not a fit to extend for Trailmark's actual differentiator. |

**Bottom line, stated bluntly:** No existing OSS project combines (a) an OS-level global-hotkey always-on-top capture surface with (b) a typed point + attached source unit with (c) topic/sub-topic grouping and (d) numbered, cited multi-format report export, on Windows, as a lightweight native app. Zotero (citation engine) and Obsidian's Pandoc plugin (export pipeline) are worth **stealing substrate from**, not migrating to. Memos is the nearest in *spirit* (quick-capture-first) but is architecturally a self-hosted web service, not a frameless native overlay, and has zero citation/report machinery. **Building Trailmark's capture UX standalone remains justified; the recommendation is to keep building it, while adopting citeproc-py/CSL and studying the Obsidian-Pandoc plugin and Zotero's translation-server for the parts that are genuinely solved problems.**

Note: Standard Notes, AnyType, Trilium/TriliumNext, Danswer, Khoj, Reor, AppFlowy, Notesnook, Wallabag, Paperless, Focalboard were searched for or considered; none surfaced evidence in this session of a global-hotkey instant-capture-with-citation-report feature closer to Trailmark's shape than the five compared above, so they are not detailed individually here — flag as **not found**, not **confirmed absent**, since a shallower search pass was used for this tail.

## 3. Export/templating subsystems worth lifting wholesale

- Star counts marked "confirmed" came directly from a fetched search-result snippet quoting GitHub's own count at query time (Sept 2026); all are approximate and will drift.
- Several license claims (Zotero translation-server's own LICENSE file, Joplin's exact license text, SiYuan's exact license, Karakeep's exact license, winocr's package license) were **not independently fetched and re-read** in this pass — they are stated as commonly-known/widely-reported but should be re-verified against each repo's LICENSE file before any code is copied or a dependency is shipped.
- "Last commit" / activity claims for Trilium/TriliumNext and Logseq could not be pinned to a specific fetched date in this session (search results returned navigational pages, not commit-graph data) — reported as **unverified**, not asserted.
- Standard Notes, AnyType, Danswer, Khoj, Reor, AppFlowy, Notesnook, Wallabag, Paperless, Focalboard received only a shallow pass; absence of a global-hotkey capture feature for these is **not confirmed** either way and should not be read as "verified absent."
